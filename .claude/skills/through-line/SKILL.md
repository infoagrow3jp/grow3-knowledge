# through-line：材料から、切れ目と次の問いを返す

## 何のためのスキルか

小林さんの見立てを、根拠をたどりながら別の角度から揺さぶるための入口。
答えを出すスキルではない。支援の進め方を決めるのは小林さん。

- 7段は、毎回通す工程ではない。必要になったときに掘る7つの視点
- どの段から入ってもよい。全部を埋めることを求めない
- 実験的な支援プロセスであり、実案件での検証は済んでいない（DEC-030）

## 正本の位置づけ（複製禁止）

- 一本線の約束・目印・検査の内容：`through-line/framework/line_map.md`
- 各段の役割と禁止事項：`through-line/agents/01_numbers.md`〜`07_people.md`
- register の形：`schemas/organization-diagnosis/`（設計は `docs/organization-diagnosis_schema設計メモ_v0.1.md`）
- モノサシ台帳の形：`schemas/through-line/monosashi.schema.json`
- 数字の計算：`financial_calc.py` と `docs/financial-analysis_指標定義書_v0.2.md`
- 記入例：`through-line/fixtures/fictional-signage/`（架空の1社）

約束や算式を、このファイルに書き写さない。必要になったら、その場で正本を読む。

## Step 0：置き場所を決める（最初に必ず）

実案件の register とモノサシ台帳は、顧客に紐づく記録。**このリポジトリ（公開）の中には置かない。**

- 案件フォルダは、リポジトリの外の、非公開の案件領域に置く
- 場所が分からなければ、小林さんに一度だけ聞く。以後は同じフォルダに書き足す
- リポジトリ配下のパス（`clients/` を含む）を指定されたら、書き込まずに、公開リポジトリである旨を伝えて確認する
- 顧客名・個人名を、リポジトリ内のファイル・commit メッセージ・ログに書かない

## Step 1：材料を受け取る

あるものだけ受け取る。足りないものを、先に要求しない。

- 財務分析のメモや決算書、バリューチェーンの整理、打合せの記録、現場の観察、工程の記録など
- 小林さんの見立て（「ここが詰まっとる気がする」など）も材料。仮説として受け取る

## Step 2：register に整理する

受け取った材料を、organization-diagnosis の register に書く。書けるものだけ書く。

- 層と工程の目印は `extensions.through_line` に置く（`line_map.md` の「目印」）
- 該当する段の `agents/` だけを読む。全部を読んで全部を埋めようとしない
- 守ること：
  - 材料に無い事実・数値・発言を作らない。発言は原文のまま
  - 数字は `financial_calc.py` で出す。暗算しない。算定できないものを 0 にしない
  - 数字から因果へ直接飛ばない。矢印には、流れの測定か現場の証拠を付ける
  - 仮説は「確認中」から始める。小林さんの見立ては、小林さんの仮説として記録する
  - AI が制約を決めない。感覚の段階の見立てに、専門用語で診断を確定させない
  - 見立てが変わったら、前の仮説を消さない。状態を変え、何が見立てを変えたかを残す

## Step 3：問いを出す

```
py -X utf8 -I through-line/tools/line_questions.py <案件フォルダ>
```

- register が揃っていなくてよい（無いものは空として扱われる）
- 「読めない」と出たら、register の形が schema に合っていない。形だけを直して、もう一度回す
- 「形式の直し」は、原資料と照らして一意に直せるものだけを直す。直せなければ聞く
- 「根拠の欠落・不一致」は、直さない。参照先が無いのは、まだ渡されていないだけかもしれない。元の材料に当たり、無ければ小林さんに聞く
- **検査に通すために、根拠・参照・数値・発言を消したり書き換えたりしない。** 外れたままでよい。外れていること自体が、次の問いの材料

## Step 4：小林さんへ返す

出力をそのまま貼らない。次の3つを、その会社の言葉で、短く返す。

1. **つながっているところ**：どの数字から、どの流れ・どの現場まで、根拠つきでたどれるか
2. **切れているところ**：どこから先に根拠が無いか
3. **次の問い**：3つまで。次の訪問や次の分析で確かめられる形にする

返し方の約束：

- 問いは、今回の材料がある段と、相談の目的を起点に選ぶ。出力は 1 数字 から順に並んでいるが、その順に選ぶ必要はない
- 前の段の根拠が足りないときは、その限界を一言添える。ただし、前の段が未入力という理由だけで、現場の判断や別の可能性を探る問いを外さない
- 根拠の無い因果や制約を、断定しない
- 材料の中に、小林さんの見立てと別の説明になりうる発言や事実があれば、それを捨てずに問いに使う
- ID・記号・JSON・schema の用語を見せない（聞かれたら出す）
- 問いは、答えの誘導にしない。小林さんの見立てと違う説明が成り立つなら、1つだけ添える
- 小林さんの見立てを言い換えて、AI の提案として出さない
- 検査で外れたところが無くても、「正しい」とは言わない。検査が見るのは形だけ
- 材料が少ないことを、不備として扱わない
- 対話から出た、線に乗らない発見（数字に表れていない価値など）を、線に合わないからと捨てない。そのまま記録する

## Step 5：次に材料が来たら

同じ案件フォルダに書き足し、Step 3 から回す。前回の問いに答えが出たかを、最初に一言で返す。

## 線を確定させるとき

モノサシを業務の基準や評価に使う前など、線を確定させる場面では、合否を出す検査を使う。

```
py -X utf8 -I through-line/tools/line_check.py <案件フォルダ>
```

評価に使うかどうかは、人事制度設計OSの確認を経てから判断する（`agents/07_people.md`）。
