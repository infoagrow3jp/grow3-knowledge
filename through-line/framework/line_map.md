# 一本線（through-line）— 数字から人までをつなぐ

仮称。フォルダ名も仮で、変えてよい。

財務の数字、工程の流れ、現場の発言を、根拠つきの因果でつなぎ、会社全体を縛っている制約を1つに絞り、
その制約に効く判断をモノサシにして、育成と評価につなぐ。そのための段取りと検査。

1〜6段のデータは、すべて organization-diagnosis の5つの register に入る。
足したのは、段ごとの役割定義（agents/）、register の上に載せる目印（下の「目印」）、段をまたぐ検査（tools/line_check.py）、モノサシの台帳の schema 1つ（下の「モノサシ台帳」）、そして財務側へ入れる計算の提案（proposals/）。

---

## 7つの段

| 段 | やること | 入る register | 使う既存の部品 |
|---|---|---|---|
| 1 数字 | 決算・MQ を測定として入れる | evidence（MEASURED・finance） | financial-analysis のエージェント、`financial_calc.py`、指標定義書 |
| 2 流れ | 工程ごとの完了件数・滞留・待ちを測定として入れる | evidence（MEASURED・flow） | Evidence の測定型 |
| 3 現場 | Lens で引き出した発言、立ち会いの観察を入れる | evidence（REPORTED / OBSERVED / DOCUMENTED・field）、patterns | Practice Lens、org-diagnosis-registers スキル |
| 4 因果 | 工程の変数どうしを、根拠つきの矢印で結ぶ | causal | Causal の矢印・連鎖・ループ |
| 5 制約 | 全体を縛っている工程と資源を、構造の仮説として置く。確かめ方を決める | hypotheses、verification_actions | Hypothesis、Verification action |
| 6 判断 | 制約に効く判断の場面を、モノサシ化の聞き取り対象に指定する | verification_actions（additional_interview） | モノサシ化（判断の見え方・線のすり合わせ） |
| 7 人 | 聞き取りで出たモノサシを、育成／業務の基準／評価の用途に仕分ける | monosashi.json、材料メモ | 人事制度設計OS |

1〜5 は organization-diagnosis の Evidence → Pattern → Hypothesis → Causal → Verification action と同じ順。
違うのは、証拠を「数字／流れ／現場」の3層に分け、制約を1つに絞るところまで求める点。

## 目印（extensions.through_line）

organization-diagnosis の各 item は `extensions` を持てる。一本線の目印は、すべて `extensions.through_line` に置く。
schema は中身を見ないので、`tools/line_check.py` が見る。

| 置く場所 | キー | 値 |
|---|---|---|
| evidence | `layer` | `finance`（決算・MQ）／`flow`（工程の流れの実測）／`field`（発言・観察・文書） |
| evidence | `stage` | 工程。語彙は practice-lens の `valueChainStage`（intake / survey / design / production / handoff / install / close / after / support）。finance は無くてよい |
| evidence | `lens_ids` | その証拠を引き出すのに使った Lens（任意） |
| evidence | `measure` / `item_type` | 測定の種類。`throughput`（工程の完了件数）／`wait`（待っていた時間）／`constraint_available`・`constraint_used`（制約資源の使える量・使った量）／`constraint_per_item`（1件が占有する制約資源の量）／`mix_count`（種類ごとの件数）／`unit_margin`（1件あたりM）。`item_type` は案件の種類 |
| hypotheses | `kind` | `constraint_candidate`（制約の仮説）。ほかの仮説は付けなくてよい |
| hypotheses | `stage` / `resource` | 制約の工程と、縛っている資源（人・設備・判断） |
| hypotheses | `next_constraint` | `{stage, basis_evidence_ids, note}`。この制約をほどいたとき、次に縛る見込みの工程 |
| hypotheses | `constraint_unit` / `used_evidence_id` / `available_evidence_id` | 制約資源の単位と、使った量・使える量の測定 |
| causal（矢印） | `from` / `to` | それぞれ `{layer, stage}`。矢印の両端の変数が、どの層・どの工程のものか |
| verification_actions | `kind` | `constraint_measurement`（制約を確かめる測定）／`monosashi_selfreport`・`monosashi_interview`（6段への受け渡し）／`monosashi_trial`（聞き取りの後、次の案件で一つ試すこと）／`finance_recalc`（1段への戻し。順位表 `ranking` を持つ）／`improvement_scenario`（改善シナリオ `scenario` を持つ）／`structure_experiment` |
| verification_actions | `judgment_scene` / `case_selection` / `person` / `responsible` / `lens_ids` | `monosashi_interview` のとき。聞き取る場面、案件を選ぶ基準、本人、その判断の責任者、使う Lens |

工程の語彙を practice-lens と揃えたのは、Lens の `value_chain_stages` と同じ言葉で、証拠・矢印・制約を引けるようにするため。

## 検査（tools/line_check.py）

先に schema 適合（Draft 2020-12 + 日時・日付の形式）を見る。違反があれば、その先は検査しない。

| 記号 | 見ること | 外れたら |
|---|---|---|
| 参照 | register をまたぐ ID が実在する。case_id が同じ。棄却した証拠を根拠にしていない。主要な証拠が supporting に入っている | FAIL |
| L1 | すべての証拠に層がある。finance と flow は測定、field は測定以外。工程が語彙にある | FAIL |
| L2 | **数字から因果へ直接飛ばない。** 矢印の根拠に、流れの測定か現場の証拠が1件以上ある。根拠ゼロの矢印は無い | FAIL |
| L3 | 制約の仮説は構造の層。制約とした工程の流れの測定と、現場の証拠が、両方とも根拠にある。ほかの工程が制約である可能性を検討している。確かめる測定が決まっていて、何が出たら強まり／弱まるかが書いてある | FAIL |
| L4 | 流れの測定が2工程以上ある（制約は工程どうしの比較でしか言えない） | FAIL |
| L5 | 制約の工程から財務の変数まで、矢印がつながっている | FAIL |
| L6 | 支持された（SUPPORTED）制約の仮説は1つまで | FAIL |
| L7 | 制約の仮説に、モノサシ化の聞き取り対象（判断の場面）が指定されている | 支持済みなら FAIL、確認中なら WARN |
| L8 | 書かれた Lens の ID が practice-lens にある | WARN |
| L9 | 制約の仮説に、ほどいたあと次に縛る工程が書かれている。その根拠が、実在する流れの測定で、次に縛る工程そのものの測定を1件以上含む（ほかの工程の測定を比較に足すのは構わない） | 工程が無ければ WARN、根拠が無い・違うなら FAIL |
| L10 | 制約資源あたりMQ の順位表：分子は1件あたりM の測定、分母は制約資源を**占有した量**の測定（待っていた時間は不可）。分子は 円/件、分母は 制約資源の単位/件。分子と分母の期間・対象が揃っている。数値が元の測定と合い、値が分子÷分母と合う | FAIL |
| L11 | 改善シナリオ：シナリオと明示している。上流の上限と需要の上限を置いている。上限の値が元の測定と合う。**計算に使う測定どうしの、単位と期間・対象が揃っている**（使える量は 単位/期間、占有量は 単位/件、件数は 件/期間、M は 円/件）。**数値を、元の測定と計算関数から出し直して照らす**（1件あたり占有量の加重平均、制約資源から見た上限＝使える量÷改善後の占有量、改善後の件数＝上限の最小値、上限を決めているもの、増える件数、増えるMQ＝増える件数×1件あたりM） | FAIL（測定の裏づけが無い仮定は、件数を WARN で出す） |
| L12 | 制約資源の使える量と使った量が測られている。両者の単位と期間が揃っている | 測られていなければ WARN、揃っていなければ FAIL |
| M1 | モノサシの元の証拠が実在し、現場の証拠である | FAIL |
| M2 | モノサシが、制約の仮説につながる聞き取りから出ている | 評価へ出すなら FAIL、それ以外は WARN |
| M3 | 業務の基準に採用しているものは、認定されている | FAIL |
| M4 | 評価へ出すものは、認定されている。相談線なら線の4基準を通している。本人の情報と権限を確かめている。採用には人事制度設計OS の確認が済んでいる。実案件が2件に満たないものを採用するなら、例外を認めた人と理由が書いてある | FAIL（2件に満たないものを OS へ出すだけなら WARN） |
| M5 | 認定前のものを育成に使うときは、暫定と明示している | FAIL |
| M6 | `source_case_count` が、元の証拠に付いている異なる出来事（occurrence_key）の数と合っている | FAIL |

L2 は organization-diagnosis の設計メモの「MEASURED から因果へ直接飛躍しない」を、機械で見られる形にしたもの。
L3〜L6 が、制約を1つに絞るための約束。**検査が見るのは形だけ。** その工程が本当に制約かどうかは、測定の結果を見て人が判断する。

**L5 は、財務への効果を保証しない。** 矢印が財務の変数までつながっている、という形を見ているだけ。制約をほどいて完了件数が増えても、MQ が同じだけ増えるとは限らない。

**制約は動く。** 制約を見つける → ほどく → 制約が別の工程へ移る → 全体を測り直す、の繰り返しになる。架空の例では、施工が週7件から上がっても、上流の完了実績は設計9件・製作10件なので、上流の処理量がこの実績を超えないと仮定すれば、次に縛るのは設計。これを `next_constraint` に書く（L9）。

## 問いとして読む（tools/line_questions.py）

`line_check.py` は、線が揃っているかを合否で出す。線を確定させるとき（モノサシを業務の基準や評価に使う前など）に使う。
ふだんの支援では、同じ検査を `line_questions.py` で回し、結果を「つながっている所・切れている所・次の問い」として読む。

- 検査の中身は `line_check.py` と同じ。足しても変えてもいない
- register が揃っていなくてよい。無いものは空として扱う。どの段から入ってもよい
- 外れた項目を、「次の問い」「根拠の欠落・不一致」「形式の直し」に分けて出す。合否は出さない
- 根拠の欠落・不一致（参照先が無い、など）は、AI が直さない。検査に通すために、参照や根拠を消さない
- 7段は、毎回通す工程ではない。必要になったときに掘る7つの視点として使う

呼び出しの手順は `.claude/skills/through-line/SKILL.md`。

## 制約資源あたりMQ と、改善シナリオ（proposals/）

5段で制約が決まったら、1段（数字）へ戻す。ここで使う計算は、**財務側へ入れる提案**として `proposals/` に置いた。正本ではない。

- `proposals/indicator-definition_6-1_addendum.md`：指標定義書 §6-1 の「制約資源あたりMQ」に足す、算式・分母の取り方・計算条件の案
- `proposals/constraint_calc.py`：その計算の案。`python3 -I proposals/constraint_calc.py` で最小の数値例の検算が走る

決めたこと：

1. **分母は、制約資源を占有した量。待っていた量ではない。** 班員が班長を待った時間（2.1時間/件）は分母にしない。分母は、班長が判断対応に使った時間
2. **制約資源の使える量と使った量も測る。** 使用率が低ければ、そこは制約ではない
3. **同じ期間で測ったものどうしで計算する。** 1件あたりM は、流れを測った4週間の案件から、種類ごとに出す。年間の決算の数字で割らない
4. **改善後の件数は、いちばん小さい上限で決まる。** 制約資源から見た上限、上流の工程の上限、需要のうち、いちばん小さいもの
   - **実績値・能力の上限・シナリオ上の仮定を分ける。** 上流の完了実績（測定）は、その工程が処理できる最大の量ではない。完了実績を上限に使うなら、「処理量は現状の実績を超えない」を仮定として書く（架空の例の A4）。能力の上限を測ったなら、そちらを使う
5. **シナリオは見込みではない。** 仮定を1つずつ書き、測定の裏づけがあるかどうかを分ける。需要も仮定として明示する。年換算はしない（指標定義書 §6-1「Qの需要予測を根拠なく置かない」）
6. **制約が動いたら、分母を替える。** 古い制約資源あたりの順位は、もう使わない

置き場所は、新しい schema ではなく既存の欄。測定は evidence（測定型）、順位表は `finance_recalc` の検証の `ranking`、シナリオは `improvement_scenario` の検証の `scenario`。
シナリオを検証（verification_actions）に置いたのは、「何が出たら強まり／弱まるか」を一緒に書けるから。シナリオは、確かめるべき予想として持つ。

## モノサシ台帳（schemas/through-line/monosashi.schema.json）

一本線で足した schema は、これ1つ。6段の聞き取りで出た「会社に残すもの」を、案件ごとに持つ（`monosashi.json`。非公開の案件領域に置く）。

足した理由：モノサシは「こう判断する」という規範で、organization-diagnosis の register（証拠・繰り返し・仮説・因果・検証）のどれにも当たらない。
仮説の register に入れると、「会社について言えること」と「会社が決めたこと」が混ざる。practice-lens と同じく、封筒だけ別に持ち、部品（ID・日時・機密度・拡張領域）は common.schema.json から `$ref` で借りた。

持つもの：
- 3分類（観察ポイント／選択ルール／相談線）、モノサシの文、任せる仕事、判断の場面
- 元になった聞き取りと証拠、何件の案件から出たか
- 状態（候補／認定／保留）。認定なら、認定した責任者の役割・日付・理由
- 用途ごとの扱い（育成／業務の基準／評価）と、止めている理由
- 相談線にだけ当てる、線の4基準の検証の状態
- 本人が情報と権限を持っているかを確かめたか、人事制度設計OS の確認が済んだか

用途ごとの条件：

| 用途 | 使ってよい条件 |
|---|---|
| 育成（1on1・振り返り） | 候補の段階から。認定前は「暫定」と明示 |
| 業務の基準（OJT） | 顧客の責任者による認定 |
| 評価（等級別の期待行動・評価項目） | 認定＋相談線なら4基準＋本人の情報と権限の確認。採用には人事制度設計OS の確認 |

grow3-knowledge に入れるときは、`schemas/through-line/monosashi.schema.json` に置く（検査はそこを先に探す）。

## 架空の1社を通して分かったこと

`fixtures/fictional-signage/` は、看板の製作・施工をする架空の会社（実在の会社・人物とは無関係。数値・発言・聞き取りの結果・認定はすべて架空）。
33件の証拠、1つのパターン、4つの仮説、5本の矢印、7つの検証、3つのモノサシを、schema と検査に通した。**1段から7段まで流れ、そこから1段へ戻るところまで回った。**

6段では、架空の聞き取り結果を入れた。聞き取りで「判断は班長がするもの、という前提がある」という仮説が弱まり、「班長が見ているところが班員に渡っていない」という別の仮説が立った。
7段では、モノサシ3つを用途ごとに仕分けた。1つは認定して OJT に使い、1つは候補のまま1on1 の材料にし、1つは保留にした。評価項目への採用は、3つとも止めている（`people_memo.md`）。
1段への戻しでは、案件の種類ごとの制約資源あたりMQ と、改善シナリオを出した（`scenario_memo.md`）。1件あたりM がいちばん大きいのは大型だが、班長の時間あたりでは標準がいちばん高い。
シナリオでは、班長の時間から見れば週11.1件まで流せるが、設計の完了実績が週9件なので全体は9件で止まり、制約は設計へ動く。ただしこれは「設計の処理量が現状の9件/週を超えない」という仮定のもとでの結果で、設計の能力の上限は測っていない。

通してみて、次のことが分かった。

1. **制約資源あたりMQ は、定義はあるが、正本では計算できない。** 指標定義書 §6-1 は「順位付けの主指標は MQ総額、さらに制約資源あたりMQ」と定めているが、算式も分母の取り方も書かれておらず、`financial_calc.py` に関数も無い。提案を `proposals/` に置き、fixture はその提案で計算した。正本に入れるかどうかは、財務側で決める。
1b. **計算式より先に、分母を決める必要があった。** 「待っていた時間」と「占有した時間」は別の測定。待ち時間しか測っていなければ、制約資源あたりMQ は出せない。fixture には、班長が判断対応に使った時間（種類ごと）と、使える時間の測定を足した。
2. **流れの推移はパターンにできない。** Pattern は v0.1 では出来事の繰り返し（occurrence_pattern）だけで、測定値の推移（measured_trend）は v0.2 へ先送りされている。「施工の完了件数が4週続けて製作を下回る」は、今は週ごとの測定を並べて人が読むしかない。
3. **測定にも打合せの ID が要る。** Evidence は `mtg_session_id` が必須。日報や工程表のように打合せの外で取った測定は、回収した打合せにぶら下げる。fixture では「実測の回収」の回を1つ立てた。
4. **Q から MQ・G へは矢印にしない。** MQ＝M×Q は定義で、因果ではない。因果の矢印は「施工の完了件数 → Q」までで止め、そこから先は MQ会計の定義に任せた。こうしないと L2（数字だけを根拠にした矢印）に必ず引っかかる。
5. **工程の目印は schema の外にある。** organization-diagnosis には工程の欄が無いので、`extensions` に置いた。書き忘れは schema では落ちず、`line_check.py` の L1 で落ちる。
6. **モノサシを置く場所が、既存の register に無かった。** これが、schema を1つ足した理由。上の「モノサシ台帳」のとおり。
7. **聞き取りは、制約の仮説をそのまま裏づけるとは限らない。** 架空の例では、班員は班長を待たずに自分で判断していた。仮説を1つ弱め、1つ立て直す流れになった。仮説の状態（弱まった）と、反証を見つけた記録の欄が、そのまま使えた。
8. **ループは作らなかった。** この例は「受け渡し → 確認件数 → 判断待ち → 施工完了件数 → Q」の連鎖で、閉じていない。設計メモの「必ずループを作る、は禁止」に従い、連鎖のままにした。

## 6段・7段のつなぎ方

**6段（判断）** は、5段の制約の仮説から「どの判断の場面を聞き取るか」を1つ指定するところまでを register に書く（`monosashi_interview`）。
聞き取りは、既存の2枚のシートで行う。シートの内容は変えない。詳しくは `agents/06_judgment.md`。

- 先に、制約になっている資源の責任者が「モノサシ言語化シート」を書く。まだ渡せていないモノサシが、聞き取る場面を絞る材料になる
- 次に、その場面で実際に判断のズレが起きた案件を1件選び、「判断の見え方・線のすり合わせシート v0.2」で本人に聞き取る
- 再現は「視点 → 事実 → 着目点 → 解釈 → 先読み → 判断 → 行動」。本人には分類させず、面談者が翻訳する。結果は③まで持ち出さない
- ④で本人の見えと責任者の見えを比べる。⑤で会社に残すものを「観察ポイント／選択ルール／相談線」に分け、「候補／認定／保留」を付ける
- **認定するのは顧客の責任者。** Grow3 でも、この検査でもない

聞き取りの結果は、3つの道で一本線に戻る。

1. ②と④の発言は、現場の証拠として evidence に戻る。制約の仮説が強まるか弱まるかは、ここで決まる
2. ③のズレた場所は、制約をほどく手がどこにありそうかの見当になる。「必要な情報がなかった」なら4段の受け渡しの矢印、「注意が向いていなかった」なら観察ポイント、「まだ自分で決めてよい範囲だと思った」なら相談線
3. ⑥の「次の案件で一つだけ確認する」は、検証（`monosashi_trial`）として verification_actions に入る

**7段（人）** は、6段で出たモノサシを、育成／業務の基準／評価の用途に仕分ける。条件は上の「モノサシ台帳」の表のとおり。詳しくは `agents/07_people.md`。

- 候補や保留も、育成の材料には使える。ただし暫定と明示し、守るべき決まりとしては伝えない
- 業務の基準にするのは、顧客の責任者が認定したものだけ
- 評価項目にするかどうかは、ここでは決めない。人事制度設計OS の設計プロセスに渡し、等級別の役割・権限、観察できるか、公平に評価できるか、運用できるかを確かめてから
- 相談線は、等級定義の軸「裁量と責任」の等級差の材料。観察ポイントと選択ルールは、能力・役割評価の行動の書き方の材料
- 渡すのは制約に効く判断だけに絞る（OS の Gate3）

## 確かめていないこと

- 6段は、「判断の見え方・線のすり合わせシート 実地テスト用 v0.2」と「モノサシ言語化シート」の実物を読んで書いた。ただしシート v0.2 は実地テスト用で、対照案件との比較・反実仮想・線の4基準検証は行わない。そこで出る線の候補は、1件から出た弱い候補である
- 評価項目への採用に、件数の一律の基準は置いていない。原則は「異なる場面や担当者でも当てはまることを確かめる」。確かめられていなければ保留し、例外として採用するなら、認めた人と理由を書く。検査が見るのは、2件に満たないものを採用したときに、その例外の記録があるかどうかだけ
- 6段と7段のデータは、架空の聞き取り結果と架空の認定で作った。段どうしの受け渡しが成り立つことは確かめたが、実際の聞き取りで同じように取れるかは確かめていない
- 制約資源あたりMQ とシナリオの計算は、提案中の `proposals/constraint_calc.py` による。正本の `financial_calc.py` と指標定義書には、まだ入っていない
- 単位と期間の検査は、文字列が一致するかを見ているだけ。「時間」と「h」のような書き方の違いは、不一致として落ちる。単位の換算はしない
- 案件構成の測定は、単位表記の統一とpopulationの一致まで確認する。単位表記中の期間の長さと、実際の測定対象期間との一致は人が確認する
- シナリオの仮定5つ（判断対応時間がどれだけ減るか、案件の構成、需要、上流の処理量が現状の完了実績を超えないこと、増える案件のM）は、測定の裏づけが無い。検査は、裏づけの無い仮定の件数を警告で出すだけで、仮定がもっともらしいかは見ない
- 案件の種類ごとの1件あたりM は、F を種類別に配賦せず、`calc_mq` に F＝0 を渡して `m_unit_margin` だけを使った。この使い方でよいかは、財務側で確かめていない
- 検査の L1〜L12・M1〜M6 は、この1例と、わざと変えた60通り（落ちるべきもの53、警告だけで通るべきもの6、そのまま通るべきもの1）で確かめただけ。業種や型が違う会社で足りるかは分からない
- organization-diagnosis の正式な validator（設計メモの100の責務）は未実装。ここの「参照」検査は、その一部を先に書いたもの
