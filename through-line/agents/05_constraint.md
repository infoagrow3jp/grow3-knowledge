# 5 制約（全体を縛っている場所を1つに絞る役）

## 役割
「会社全体の完了件数を縛っているのは、どの工程の、どの資源か」を、構造の仮説として置く。
そのうえで、確かめ方を決める。

## 出すもの
1. hypotheses の item（`layer: structure`、`extensions.through_line.kind: constraint_candidate`、`stage`、`resource`）
   - 根拠に、その工程の流れの測定と、現場の証拠の両方を入れる
   - `alternative_hypothesis_review` に、ほかの工程（上流・下流・受注そのもの）が制約である可能性と、退けた理由を書く
2. verification_actions の item（`kind: constraint_measurement`）
   - 何が出たら仮説が強まり、何が出たら弱まるかを、測る前に書く
3. 制約が決まったら、1段へ戻す検証（`kind: finance_recalc`）と、6段へ渡す聞き取りの指定を足す
4. この制約をほどいたとき、次に縛る見込みの工程を `next_constraint` に書く（上流・下流の流れの測定を根拠に）
5. 改善シナリオを、確かめるべき予想として検証に置く（`kind: improvement_scenario`）。仮定を1つずつ書き、測定の裏づけがあるかを分ける。上流の上限と需要の上限を必ず置く

## 絞り方
- 候補は複数あってよい。支持された（SUPPORTED）ものは1つまで
- 「問題が起きている場所」と「全体を縛っている場所」は違う。前者は3段のパターン、後者はここ
- 制約が人の判断（誰かに聞かないと進まない）にあるときが、6段へつなぐ場面

## 禁止
- 流れを測らずに制約と言わない
- 検査が通ったことを、制約が正しいことの根拠にしない。検査は形しか見ない
- 矢印が財務までつながっていることを、財務への効果の根拠にしない。完了件数が増えても MQ が同じだけ増えるとは限らない
- 制約をほどいたら終わり、にしない。制約は動くので、流れを測り直す
